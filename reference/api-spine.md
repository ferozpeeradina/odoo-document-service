# Shared API spine
Base path /api/v1. Bearer Firebase ID tokens are verified server-side; active memberships grant roles. Scoped pk_ API credentials permit headless integrations and can be revoked. Demo tokens are allowed only in explicit demo/test mode with synthetic data. Envelope: {data}; errors: {error:{code,message,details?},requestId}. Never expose raw provider errors/secrets.
Feature modules export async register(app,spine). Use Fastify JSON route schemas for OpenAPI and validation; all side effects live behind API commands, never the UI.
Spine: actor(request), requireStaff(request), requireOwner(request); command(actor,name,idempotencyKey,input,async tx=>result); audit(tx,actor,event,targetId,details); ok(data).
Commands may supply an optional sixth `prepare` callback for provider checks outside transactions. Stored results replay before preparation; a failed preparation rechecks a concurrent commit. The mutation callback still validates saved revisions inside its transaction.
Store: get(tenantId,kind,id), list(tenantId,kind,{limit,cursor,where}), atomic(tenantId,callback).
Transaction: get(kind,id), list(kind,options), put(entity). Read collection queries before staging writes; Firestore reads must precede writes. Record envelope has UUID id, tenantId, kind, schemaVersion=1, revision, UTC createdAt/updatedAt, data. record/revise helpers are in core/records.ts. Financial totals use integer CAD cents and decimal unit prices.
Core GET projects/organisations/contacts are staff-only and paginated. GET projects/:id/workspace joins bounded project links and original RFQs. Customer feature must create explicit safe projections and derive organisation from membership; never serialize raw workspace data.
Reserved feature route contract:
- foundation: POST /organisations, /contacts, /projects; PATCH /projects/:id; POST /projects/:id/quotes, /projects/:id/orders, /projects/:id/invoices; POST /invoices/:id/payment-requests, /invoices/:id/offline-receipts; GET /invoices/:id/balance, /ledger, /audit, /export; PATCH /settings/business.
- customer: POST /public/rfqs; GET /portal/projects, /portal/projects/:id, /portal/invoices, /portal/contacts; POST /invitations, /invitations/:id/accept; DELETE /memberships/:id; POST /projects/:id/form-requests; GET/POST /forms/:id; POST /form-requests/:id/revoke.
- ai: POST /cards/extract, /cards/:id/verify; POST /commands/interpret, /commands/:id/confirm; GET /jobs/:id, /operations/workflows; POST /internal/jobs/recover; POST /internal/jobs/:id/run.
- integrations: POST /documents, /documents/:id/signature-requests; GET /documents/:id, /documents/:id/artifacts; POST /webhooks/dms; POST /payment-requests/:id/checkout; POST /webhooks/stripe.
Headless command payloads require Idempotency-Key for business mutations. Never call provider network inside a Firestore transaction; persist intent/outbox, then dispatch. Exact provider methods and feature handlers are lane-owned; coordinate by handoffs.
ListOptions additionally supports orderBy:{field:'createdAt'|'updatedAt'|'data.field',direction:'asc'|'desc'} and range:{createdAt:{gte:UTC,lte:UTC}}. Ordered cursors are opaque, query-bound, with ID tie-breaks; ordering applies before pagination. Matching Firestore indexes are required. Headless owner commitments use a verified Firebase owner ID token obtained through the Firebase REST authentication API; scoped pk_ credentials remain staff and cannot elevate to owner or grant memberships. The browser is optional for either authentication route.
All workers implement their UC IDs with synthetic fixtures and meaningful HTTP journeys. No test can count UC coverage merely by listing a title.

Guided replacement revocation supports an optional recipientSnapshot with projectId, contactId, organisationId, type, allowedFields, expectedContactRevision and expectedRecipientEmail. Owner permission, recipient eligibility, frozen bindings and submission state are checked in the revocation transaction. AI replacements use this guarded domain endpoint; no direct AI form mutation bypass is permitted. Typed command_review_required responses bind the rejected proposalId and exact noDispatch proof; replacement_review_required responses identify safe review and whether the original link was already revoked. Unknown outcomes keep the original reviewed operation.
